# 家装 AI 智能下单工作流 — 口语演讲稿

> 面向智能科学与技术专业背景，通俗解读一个 AI Agent 驱动的采购订单工作流项目

---

## 开场白

各位老师、同学好，今天我想跟大家分享一个我最近在研究的项目——**家装 AI 智能下单工作流**。

这个项目的背景其实特别简单：我有个朋友在佛山做贸易公司，帮助海外客户采购中国的装修材料和工程物资。他的核心痛点是——订单信息乱七八糟，客户通过邮件、微信、WhatsApp 甚至手绘图纸发过来的需求都不一样，而且随时可能改。人工整理起来特别费时间，还容易出错。

那我的问题就是：**能不能用 AI Agent 把这个流程自动化？**

今天我就把这个项目从头到尾拆解一遍，争取让非计算机专业的同学也能听懂我们在做什么。

---

## 第一部分：问题是什么

大家想象一个场景——

一个酒店项目需要采购大批家具。客户可能先发一封邮件说"我要100套这个尺寸的床"，然后第二天在微信里说"尺寸不对，改一下"，第三天又发一张手绘图纸过来。

结果是什么？采购人员要在邮件、微信、图片、PDF 之间来回翻，找最新的版本，一不小心就用错了旧数据，下单给工厂，导致返工、延误、甚至赔偿。

这就是**多源信息 + 版本混乱 + 人工整理**的典型痛苦。

我总结了这个问题的三个关键词：

**1. 信息散**：订单来源分散在七八个地方，没有统一入口。
**2. 版本乱**：需求不断变化，但人工很难判断"哪个才是最最新的那个"。
**3. 人工重**：大量的复制粘贴、分类核对工作，耗时长、错误成本高。

---

## 第二部分：我们的方案

那怎么解决？我把这个工作流拆成了 **8 个层级**，就像一条流水线，每个环节做一件特定的事。

我来一个个说——

### 第1层：数据入口

首先，用户把各种文件传进来。邮件附件、微信截图、PDF、Excel，都行。

技术上这里做了一个妥协：MVP 阶段（demo）先不做自动化的邮件抓取，而是让用户手动上传。为什么？因为个人微信自动化在大陆有合规风险，我们先验证核心价值，把难的留到后面。

### 第2层：原始资料库

传进来的文件自动打标签——来自哪个平台、是什么类型、谁发的、什么时候。这是给后面"版本判断"打基础的。

### 第3层：AI 解析层（核心新增：置信度评分）

这是我觉得最有意思的地方。

我们用 **PaddleOCR** 识别图片里的文字，用 **大模型（LLM）** 把文字里提取出结构化数据——比如床的尺寸、材质、数量。

但光提取还不够，**每个字段还打一个"置信度"分数**。比如模型判断"这个尺寸是450mm"，置信度是 95%；但"材质是橡木"只打了 70%。

为什么这么做？——因为置信度决定了后面怎么处理。置信度高的字段，系统可以自动通过；置信度低的，需要人工确认。

这就是**数据驱动决策**，不是所有东西都扔给人，而是让机器先干活，人只处理不确定的部分。

### 第4层：订单数据库（新增：版本轨迹）

所有提取出来的数据存入 PostgreSQL 数据库。

关键设计是——**每次修改都生成新版本，而不是覆盖旧数据**。比如 5 月 20 日客户说床的尺寸是 450mm，5 月 22 日改成 500mm，系统会同时保留两个版本，标注时间戳。

这解决了一个核心产品问题：**"哪个版本是最新的？"**

而且每个字段都关联到原始证据——是哪个文件、哪条消息提取出来的，人工可以一键查看，从根本上避免争议。

### 第5层：规则引擎层（核心：冲突分级 + 规则可配置）

这一层是整个系统的"大脑"。

当订单数据进来后，规则引擎会检测三类问题：

**致命冲突**：比如数量填了 0，或者床的宽度和高度填反了，这种必须强制人工处理。

**一般冲突**：比如颜色描述不一致，系统会标出来建议值，但不强制。

**缺失字段**：比如缺少供应商信息，系统自动推荐一个。

重点来了——**这些规则是可配置的**。运营人员不需要改代码，直接改配置参数就可以调整规则逻辑。这对于快速迭代非常重要。

另外，第5层还用到了一个 **AI Version Agent**，它不只看时间戳来判断最新版本，而是理解上下文语义。比如客户说"还是用之前那个规格"，AI 能理解这是在引用哪个版本。

### 第6层：确认与审批层

基于前面的置信度评分和冲突分级，系统做了**分级确认**：

- 高置信度 + 无冲突 → **自动通过**
- 中置信度 + 一般冲突 → **轻量确认**，只核异常项
- 低置信度 + 致命冲突 → **完整确认**，逐条核对

这样做的好处是：人工不需要看所有字段，只需要看"真正有问题的那些"。理论上可以减少 70% 的人工确认工作量。

### 第7层：输出执行层

确认完成后，系统生成 **PDF 或 Excel** 发给工厂。

这里新增了一个"格式校验"环节——自动检查工厂要求的必填字段是否齐全。如果发现缺字段（比如少了交货日期），提前打回，而不是发给工厂之后才发现要返工。

### 第8层：发单追踪层（新增：数据迭代闭环）

这是整个系统最有特色的地方之一——**规则会自己进化**。

当同一类错误发生超过 3 次，系统会自动触发提示词优化或规则调整。比如某个项目总是把"单位是件"误解为"单位是个"，累计 3 次后，AI 会自动记住这个 pattern，下次提取会更准。

这就是**数据→规则→效率**的正向循环，自动化等级会从 L5 逐步向 L6、L7 提升。

## 第三部分：技术选型

我知道有些同学可能想了解——为什么选这些技术，不用那些主流方案？

我做了一个对比：

| 方案 | 适合做什么 | 为什么我们没选 |
|------|-----------|---------------|
| **n8n** | 通用流程自动化，API 串联 | 好用，但缺少原生版本管理和置信度概念 |
| **LangChain** | AI 优先的复杂推理 | 技术门槛高，规则不可配置，无迭代闭环 |
| **Simple RAG** | 文档问答、知识库 | 只解决提取，不解决订单建模 |
| **传统 ERP** | 标准化流程 | 刚性强，无法处理多源非结构化数据 |

我们的方案核心差异是三点：

1. **置信度驱动分层确认**——不是所有东西都让人看，而是让机器先筛选出真正需要看的。
2. **规则引擎可配置**——运营人员可以调规则，不需要程序员改代码。
3. **数据迭代闭环**——系统会从错误中学习，自动化等级会随时间自动提升。

---

## 第四部分：MVP 计划

最后说一下落地节奏。

我们不是一口气做一个完美的系统，而是分四个阶段：

**第一周**：梳理真实项目资料，定义标准订单字段和工厂 PDF 模板。
**第二三周**：开发 MVP 核心功能——文件上传 → AI 解析（含置信度）→ 结构化订单 → 冲突分级 → PDF 生成。
**第四周**：用真实项目测试，收集反馈，优化规则。
**后续迭代**：逐步接入邮件/WhatsApp，开放低风险自动发单，完善状态追踪。

MVP 的定义非常明确——**跑通"1 个项目 → 1 份生产单"的完整闭环**，其他的先放一放。

---

## 总结

这个项目的本质，是一个**渐进式自动化的 AI 工作流系统**。

不是第一天就承诺"AI 全自动下单"，而是从最痛、最高频、最容易验证价值的地方开始——把混乱的资料整理成准确、结构化、可确认、可追溯的订单文件。

当这个闭环跑通了，我们再逐步扩展自动化边界，最终实现低风险场景下的自动下单。

我觉得这个项目对于理解 AI Agent 在实际业务场景中的应用，很有参考价值。

## 附：技术术语对照表（方便非专业听众理解）

| 技术术语 | 通俗解释 |
|---------|---------|
| LLM / 大模型 | 像 ChatGPT 一样的 AI，能理解文字并提取信息 |
| OCR | 把图片里的文字"读出来"变成可编辑的文本 |
| PostgreSQL | 一种数据库，用来存储结构化的订单数据 |
| JSONB | 数据库里一种可以存"半结构化"数据的方式，便于追溯每个字段的来源 |
| 版本轨迹 | 每次修改都被记录下来，可以看到完整的变更历史 |
| 置信度评分 | AI 给自己的判断打分，90% 以上说明很有把握，70% 以下说明不太确定 |
| 规则引擎 | 一套"如果...那么..."的逻辑判断系统，决定哪些需要人工看 |
| 迭代闭环 | 系统能从错误中学习，下次自动做更好 |
